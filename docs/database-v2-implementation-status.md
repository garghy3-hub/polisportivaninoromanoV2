## Verified

- PostgreSQL project returned `ACTIVE_HEALTHY` after restore.
- 13 application tables are present in `public`, and all 13 have RLS enabled (including the two pre-existing tables).
- New normalized tables exist for seasons, teams, roster, staff, events, news identities, news revisions, media metadata, club profile, site settings and audit history.
- Existing `site_content` remains a public-only singleton; its write policies now require an active Administrator.
- Existing `admin_users` remains the allow-list and now includes `role` and `is_active`.
- Storage upload/update/delete policies are restricted to active Editor, Publisher and Administrator roles. Public object reads remain as configured by the existing public bucket.
- Privilege checks confirm anonymous users cannot insert news, browser-authenticated users cannot directly insert/update news revisions, and browser users cannot write the audit log.
- Supabase migration history contains both migrations.
- Health advisor returned no findings.
- Performance advisor no longer reports unindexed foreign keys, per-row auth initialization, or multiple permissive policies. It reports unused indexes because the new tables are empty and have not yet served application queries.

## Remaining security and integration work

- Supabase Auth leaked-password protection is still disabled. The project advisor reports this as a security warning. Enable it in the Supabase Auth password settings before enabling public account registration ([Supabase instructions](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)).
- Supabase SSR authentication is now implemented in V2: cookie-based PKCE, verified `getClaims()`, active `admin_users` role lookup, login/logout functions and a server-side guard for `/admin/*`. No Auth user has been assigned an initial Administrator. Bootstrap must happen only after a real Auth account is verified; the `admin_users` table was empty at schema creation.
- The news revision tables are deliberately read-only to browser clients. Atomic server-side create/edit/submit/review/publish/unpublish/archive/restore commands still need implementation.
- Audit rows are not yet auto-generated by database triggers. Trusted server-side transactional commands must append audit events with the content change.
- V2 content routes and admin editors still use local/demo data and local browser storage. The new database is not yet connected to the public pages or content forms; authentication alone does not make the editors persistent.
- The V2 build still needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_PUBLISHABLE_KEY` supplied in local and CI/deployment environments. No secret/service-role key belongs in browser code.
- Media object verification (file signature, image dimensions, safe object naming) must be implemented in the upload server boundary. The existing `nrm-media` bucket is public, so files uploaded there must be treated as publicly readable.

## Release status

Database foundation is installed, but the website is not production-ready. Do not expose admin mutations or switch public routes to the database until authentication, trusted server request handling, transactional editorial operations, audit writes, integration tests and runtime configuration are complete.
